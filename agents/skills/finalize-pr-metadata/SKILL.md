name: finalize-pr-metadata
description: Review an existing PR's final code and checks, flag merge blockers and obvious unpolished or duplicated code, then update its title and description via the GitHub CLI to match the full diff. Use manually just before merging a PR.
---

# Finalize PR Metadata

1. Resolve the current branch's PR once with `gh pr view --json number,url,state,isDraft,title,body,baseRefName,baseRefOid,headRefName,headRefOid,reviewDecision,reviewRequests,latestReviews,mergeable,mergeStateStatus,statusCheckRollup,commits,closingIssuesReferences`. Require `state == "OPEN"`, retain its URL and initial metadata, and pass that URL explicitly to every later `gh pr` command.
2. Establish finality with `git status --short` and by comparing `git rev-parse HEAD` to the PR's `headRefOid`, not `@{upstream}`. If an in-scope working-tree change exists, report that the remote diff omits local scope and stop. If the OIDs differ, classify the checkout as ahead, behind, or diverged when possible, report that it is not aligned with the PR head, and stop without writing.
3. Read the complete remote diff with `gh pr diff "$pr_url"`, plus the changed code, tests, docs, and commits. Derive scope from the final state, not the existing PR text or latest commit.
4. Inspect draft state, reviews and requests, mergeability, merge state, all checks and `gh pr checks "$pr_url" --required`, plus unresolved review threads via `gh api graphql`. For GraphQL, derive the base-repository host, owner, and name from the PR URL; pass them and the PR number as query variables, use `--hostname` off github.com, and paginate `reviewThreads` with `--paginate`, an `$endCursor` variable, and `pageInfo { hasNextPage endCursor }`. Treat conflicts, draft state, requested changes, missing required approval, pending/failed/cancelled required checks, and required unresolved conversations as blockers. Report failed or cancelled optional checks as non-blocking unless they demonstrate a blocker. Never declare readiness while mergeability is unknown or GitHub reports the PR blocked. Also flag correctness or security risks, missing coverage or docs, artifacts, weak naming, needless complexity, and unDRY code; separate blockers from optional polish.
5. Inventory each major theme as `<component>: <observable change>`. Make the title name the major affected areas and changes with concrete nouns and verbs, including for large multi-purpose PRs. Give each material change a concise component/mechanism/effect body bullet. Include user impact, breaking changes, and migration only when applicable; omit empty sections. Never include a `Test plan` section; under `Verification`, distinguish commands actually run from GitHub checks merely observed. Preserve verified issue-closing references verbatim; remove stale claims, boilerplate, and commit-by-commit narration.
6. Immediately before writing, compare the current `headRefOid`, `baseRefOid`, title, and body with the retained snapshot. If the head changed, stop until the checkout matches it; if the base or metadata changed, restart diff and metadata analysis. Create the body file with `mktemp` and register cleanup immediately, then run `gh pr edit "$pr_url" --title "$new_title" --body-file "$body_file"`. Re-read title and body from the same URL and compare them exactly; report any edit or comparison failure.
7. Re-read the merge gates, then report the PR URL, title change, metadata summary, blockers, and polish findings. State clearly when the PR is not merge-ready.

Use literal, implementation-specific language. Never hide changes behind generic LLM phrasing such as “harden,” “strengthen,” “improve,” “enhance,” “streamline,” “robust,” or metaphors such as “load-bearing.” Prefer “Retry GitHub HTTPS pushes across authenticated accounts” over “Harden GitHub workflows.” Do not use Conventional Commit prefixes.

Editing the captured PR's title and body is the only GitHub or repository-state write this skill authorizes. Review repository files read-only and do not invoke another workflow's fix step. Do not change labels, reviewers, assignees, milestones, projects, base branch, review state, or other PR fields. Only blockers found in an unchanged remote PR may coexist with the metadata update; local or unpushed scope changes stop it. Never create, merge, close, mark ready, comment on, commit to, or push the PR unless separately requested.
