# Update PR Metadata

Any PR state is fine. An open PR's metadata describes its projected final scope; a merged or closed PR's describes what landed, and its body is what `git log`, release notes and future readers see.

1. Resolve the PR once with `gh pr view --json url,state,title,body,baseRefOid,headRefOid,isDraft,reviewDecision,reviewRequests,latestReviews,mergeable,mergeStateStatus,statusCheckRollup,commits,closingIssuesReferences`, passing the PR number explicitly when the branch is gone (e.g. a squash merge deleted it). Retain this snapshot and pass its URL to every later `gh pr` command.
2. Build the scope from `gh pr diff "$pr_url"`, changed files and commits; the remote diff is authoritative for published code. For an open PR also read local signals of intended scope: `git diff "$headRefOid"` when `HEAD` differs, else `git diff HEAD` plus local-only commits, and untracked files via `git ls-files --others --exclude-standard`. For a merged PR the merged diff is the whole scope. Exclude unrelated work, never require a clean or aligned checkout, and report behind or diverged state without stopping.
3. Inventory each material theme as `<component>: <observable change>`. Title is one line, ~70 characters so it does not wrap in the PR list: name the primary change (1-2 concrete ones for a large multi-purpose PR, never a vague umbrella), put the rest in the body, never a comma-separated catalog of subsystems. Body is concise component/mechanism/effect bullets; include impact, breaking changes and migration only when relevant. Preserve verified issue-closing references; drop stale claims, boilerplate, commit narration, and `Test plan` or `Verification` sections. No Conventional Commit prefixes, and no generic packaging such as "harden", "strengthen", "improve", "enhance", "streamline", "robust" or "load-bearing": prefer "Initialize background tabs, protect dirty buffers, and bound shared dashboard plots" over "Harden background tab and dashboard safety".
4. Write only if the metadata actually changes: a no-op edit is churn, and on a merged PR it rewrites what reviewers approved. Re-read `headRefOid`, `baseRefOid`, title and body first, recomputing if head or base moved and restarting if title or body moved. Then run `gh pr edit "$pr_url" --title "$new_title" --body-file "$body_file"` with a `mktemp` body file and cleanup registered, adding `--add-label` for any label in `gh label list` the scope clearly warrants. Never remove an existing label; a human may have set it deliberately. Re-read title, body and labels, and report any mismatch.
5. Report the PR URL, the title change, and a metadata summary. For an open PR add merge blockers from `gh pr checks "$pr_url" --required` and unresolved `reviewThreads` via paginated `gh api graphql`: conflicts, requested changes, missing approval, unresolved required conversations, failing required checks, and unknown or blocked mergeability. Those block merging, never the metadata update; optional check failures are not blockers. For a merged PR report instead what a reader still needs: follow-ups, migrations, operational steps. Never imply the PR is final.

Only title, body and label edits are authorized. Keep repository inspection read-only and do not fix code, reviewers, assignees, milestones, projects, base branch, review state, readiness, comments, commits, or remote refs.
